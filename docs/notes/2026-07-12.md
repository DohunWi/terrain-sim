# 2026-07-12 — Phase 1: Droplet(hydraulic) erosion 완성

### 방향 갱신 — gradient의 부호, 정규화, 관성

- gradient `(gradX, gradY)`는 "높이가 증가하는 방향"을 가리키는 벡터 — 부호와 무관하게 항상 오르막 방향이라는 게 정의 자체임(`gradX`가 음수여도 그 벡터는 여전히 오르막을 가리킴, 그냥 그 방향이 `-x`일 뿐). 그래서 내리막으로 가려면 부호와 상관없이 그냥 전체를 마이너스 붙이면 됨(`-gradX`) — "음수일 땐 마이너스 붙이면 안 되는 거 아니냐"는 직관이 왜 틀렸는지, `gradX=-3`인 케이스를 손으로 대입해보고서야 정리됨.
- 벡터의 "크기"는 절댓값(`abs`)이 아니라 피타고라스(`sqrt(x²+y²)`)로 구해야 함 — x, y를 각각 독립된 스칼라로 보고 절댓값을 씌우려 했던 게 첫 시도의 실수. 벡터는 두 성분이 묶인 하나의 양이라 "길이"는 성분별로 따로 계산할 수 없다는 걸 다시 확인.
- 정규화(단위벡터화) 후 `pos += dir`로 이동 — 즉 매 스텝 이동 거리가 `speed`나 관성 크기와 무관하게 항상 정확히 1(그리드 셀 한 칸)로 고정됨. 처음엔 "왜 speed를 이동 거리에 안 쓰지" 싶었는데, 그리드 기반으로 `sampleHeightAndGradient`를 매 스텝 다시 호출해야 하니 이동 거리가 들쭉날쭉하면 한 스텝에 여러 칸을 건너뛰어 버릴 수 있음 — 단위 스텝으로 고정하는 게 bilinear 샘플링 전제를 지키는 방법. `speed`는 대신 capacity(운반량) 계산에 별도로 쓰임.
- 관성(inertia)과 유한한 스텝 크기 때문에, "gradient를 따라 내려간다"는 설계인데도 실제로는 오르막(`deltaHeight > 0`)을 밟는 스텝이 흔하게 발생함 — 관성이 이전 방향을 실어 나르는 데다, 한 스텝이 무한소가 아니라 길이 1로 통째로 이동하니 좁은 골짜기 바닥에서 반대편 벽으로 넘어가는 식의 오버슈트가 가능함(경사하강법에서 스텝이 크면 최솟값을 지나쳐버리는 것과 같은 원리). 그래서 이 케이스를 예외로 취급하지 않고 정상 케이스로 설계에 반영해야 했음(아래 capacity/deposit 참고).

### capacity / erode / deposit — 물리량과 분기 설계

- `capacity = max(-deltaHeight, minSlope) * speed * water * capacityFactor`. `minSlope`가 바닥값으로 필요한 이유: `deltaHeight >= 0`(평지/오르막)이면 `-deltaHeight`가 0 이하가 되는데, 그때도 capacity가 완전히 0이 되지 않게 하는 튜닝 파라미터.
- Deposit 로직에서 처음엔 `sediment > capacity`(초과분 처리)와 `deltaHeight > 0`(오르막) 두 조건을 OR로 묶어 "deposit이냐 아니냐"만 나누고, deposit 쪽 계산은 `(sediment - capacity) * depositFactor` 하나로 퉁쳤음. 근데 "오르막인데 sediment가 capacity 이하"인 경우(예: 방금 태어나서 sediment=0인 드롭릿이 첫 스텝에 웅덩이 가장자리로 올라가는 상황)엔 `sediment - capacity`가 음수가 돼서 오히려 sediment가 늘어나 버림(deposit인데 erode 방향으로 동작) — 실제로 일어날 수 있는 상황이라는 걸 구체적인 수치(speed=1, water=1, minSlope=0.01, capacityFactor=4, sediment=0, deltaHeight=+0.05)로 대입해보고서야 납득함. 고친 구조: `deltaHeight > 0`이면 무조건 `min(deltaHeight, sediment)`(오르막 높이만큼만, 가진 한도 내에서 내려놓기), 아니면(내리막인데 초과) `(sediment - capacity) * depositFactor`.
- 조건 두 개(`sediment > capacity`, `deltaHeight > 0`)면 논리적으로 2×2=4가지 조합이 나오지만, 실제로 필요한 분기는 "오르막이냐 아니냐"가 어떤 deposit 공식을 쓸지 우선순위로 결정하기 때문에 3갈래(deposit-오르막 / deposit-초과 / erode)로 정리됨.
- erode/deposit 두 브랜치를 나누는 조건에서, `if (deposit조건) {...} else {...}` 대신 `else`의 여집합을 손으로 다시 써서(`sediment <= capacity && deltaHeight < 0`) 검증해봤는데, 부등호를 하나씩 놓치면서(`<=`/`<` 조합 실수) 경계값(`sediment==capacity`, `deltaHeight==0`)이 어느 브랜치에도 안 걸리는 틈이 반복해서 생김 — "if의 정확한 여집합"을 매번 손으로 다시 쓰는 것 자체가 위험한 패턴이라는 걸 체감, 결국 그냥 `else`로 되돌림.

### Bilinear 분배 — thermal erosion과 다른 이유

- erode/deposit 양을 그리드 4개 코너에 나눌 때, `sampleHeightAndGradient`가 높이를 읽을 때 썼던 것과 완전히 같은 bilinear 가중치(`w00=(1-tx)(1-ty)`, `w10=tx(1-ty)`, `w01=(1-tx)ty`, `w11=tx·ty`, 합은 항상 1)를 그대로 씀 — 손으로 bilinear 전개(`lerp` 두 번 중첩)를 풀어서 이 가중치가 정확히 나온다는 걸 확인.
- Thermal erosion(2026-07-11)은 "나보다 낮은 이웃에게만" 분배했는데, droplet erosion은 4개 코너 전부에 높낮이 무관하게 분배함 — 왜 다른가 헷갈렸던 지점. Thermal erosion은 실제 그리드 셀끼리 물질을 주고받는 모델이라 "낮은 쪽으로만 흐른다"는 게 그 자체로 물리 법칙인데, droplet erosion의 4개 코너는 "물방울이 서 있는 연속적인 위치를 그리드에 근사할 때 참조하는 가장 가까운 격자점"일 뿐이라 서로 물질을 주고받는 관계가 아님. 얼마나 침식/퇴적할지는 이미 드롭릿 궤적 레벨(capacity, deltaHeight)에서 결정되고, bilinear 분배는 그 결정된 양을 그리드 위에 수치적으로 흩뿌리는 것뿐이라는 차이.

### Bounds 체크 — off-by-one을 4번 고쳐본 기록

- `x1 = x0+1`이 유효 인덱스여야 하는데(`sampleHeightAndGradient`가 4개 코너를 다 읽으니까), 이 제약을 놓치고 4번의 시도를 거쳤음:
  1. `ceil(y)*width + ceil(x) > width*height` — 2D 좌표를 1D 인덱스 하나로 뭉쳐서 비교. `x`가 단독으로 범위를 한참 벗어나도(`x=1000, y=0`) 뭉친 값(`1000`)이 우연히 `width*height`보다 작으면 통과해버림 — x, y를 독립적으로 각각 체크해야 한다는 게 핵심.
  2. `posX < 0 || posX > width` — 각 축을 분리했지만 기준값이 여전히 틀림. `posX=60`(`width=61`)이면 `x1=61`이 무효인데 `60 > 61`은 거짓이라 통과.
  3. `>`→`>=`로만 바꾸고 기준값(`width`)은 그대로 둠 — 여전히 안 잡힘.
  4. 기준값을 `width-1`로 바꿨는데 부등호는 `>`로 둠 — 정수값끼리는 `> (width-1)`이 `>= width`와 완전히 같아서, 사실상 2번 버그로 되돌아간 것과 동일. **숫자와 부등호가 세트로 같이 바뀌어야 한다**는 걸 놓쳤던 게 반복된 원인.
  - 최종: `floor(posX) >= (width-1)`이면 거부. `x1=x0+1`이 `width-1`(최대 유효 인덱스) 이하이려면 `x0 <= width-2`, 즉 거부 조건은 `x0 >= width-1`.
- 경계값 관련해서 "`posX=60`은 통과되는 게 맞지 않냐"는 반론이 나왔는데(정확히 정수일 때 `tx=0`이라 `h10`/`h11`에 가중치가 0으로 곱해지니 결과가 우연히 맞아떨어짐), `posX=60.3`(정수가 아닌 값)으로 반박됨 — `tx=0.3`(0이 아님)이면 잘못된 위치(`y0`행이 아니라 다음 행 `y0+1`의 데이터)를 읽어다가 0이 아닌 가중치로 결과에 섞어버려서 조용히 틀린 값이 나옴(크래시가 안 나서 더 위험). 드롭릿이 이동하다가 정확히 정수 좌표에 멈추는 일은 사실상 없어서, "우연히 안전한 그 한 케이스"에 기대면 안 된다는 결론.

### 함수 시그니처 설계 — 포인터 → 참조 → 구조체, void → int 리턴

- 처음엔 `dirX`/`dirY`/`posX`/`posY`를 `float*`로 받아서 `*dirX = ...`처럼 호출자 값을 직접 수정 — C의 "여러 값을 바꿔야 할 때 포인터로 넘기는" 패턴 그대로 적용.
- 상태가 늘어나면서(speed/water/sediment 추가) `Droplet` 구조체로 묶고 `Droplet&`(참조)로 바꿈 — "참조가 있으면 그냥 포인터는 필요 없는 거 아니냐"는 질문에서, 참조는 "항상 존재하고 재바인딩 안 되는" 경우에 한해 포인터보다 낫지만, nullable(연결 리스트의 `next` 같은 것), 재바인딩(순회), 포인터 연산, C API 연동 같은 경우는 여전히 포인터가 필요하다는 걸 정리함. `unique_ptr`/`shared_ptr`도 내부적으로는 raw pointer를 감싼 것뿐이라는 것도 짚음 — "포인터 자체가 위험한 게 아니라 소유권 관리가 안 되는 게 위험한 것"이라는 이 프로젝트의 핵심 주제(RAII)로 연결됨.
- 여러 float 파라미터(`inertia`, `minSlope`, `capacityFactor`, ...)도 7개까지 늘어나서 `ErosionParams` 구조체(`const&`로 전달, 안에서 안 바뀌니까)로 정리.
- 리턴 타입을 `void`→`int`(1=생존, 0=맵 밖으로 나가 사망)로 바꾼 이유: bounds 체크가 바깥 driver 루프가 아니라 `dropletStep` **내부**(이동 직후, 두 번째 `sampleHeightAndGradient` 호출 *전*)에 있어야 함 — 이동 후 위치가 이미 무효라면, 바깥 루프가 다음 iteration에서 체크하기도 전에 함수 내부에서 이미 out-of-bounds 접근이 일어나기 때문. 그래서 "이 스텝에서 죽었다"는 걸 호출자에게 알려줄 방법이 필요했음.
- `h`를 `const std::vector<float>&`에서 non-const로 바꿈(erode/deposit이 실제로 씀) — `sampleHeightAndGradient`는 읽기만 하니 `const` 유지. `const`의 의미: 컴파일러가 실수로 값을 바꾸는 걸 에러로 잡아줌 + 호출자에게 "이 함수는 읽기만 한다"는 신호 + `const` 참조는 const/non-const 아무 벡터나 받을 수 있어 더 유연함.

### 검증 — mass conservation, float vs double

- 30개 드롭릿을 순차로 뿌리는 rainfall 드라이버에서 버그 몇 개: `Droplet`을 for 루프 밖에서 한 번만 만들어서 재사용(각 "새" 드롭릿이 이전 드롭릿의 남은 상태를 그대로 이어받음) → 루프 안에서 매번 새로 선언하도록 수정. `uniform_real_distribution<int>`(타입이 `float`이어야 하는데 `int`로 선언 — 표준적으로 미정의 동작) → `<float>`로 수정. 분포 객체를 선언만 하고 실제로 `dist(rng)` 호출을 안 해서 위치가 계속 하드코딩값 → 호출 추가. `dropletStep`의 리턴값을 무시하고 계속 호출 → 리턴값을 `while` 조건에 반영.
- 드롭릿 구조체를 for 루프 안에서 새로 선언하면서, 루프 밖에 남아있던 예전 `Droplet` 변수가 shadowing으로 죽은 코드가 됐는데 mass-check 코드가 여전히 그 죽은 변수를 참조하고 있었음(항상 `sediment=0`) — 각 드롭릿이 스코프를 벗어나기 직전에 최종 `sediment`를 누적 변수(`totalCarriedSediment`)에 더해두는 방식으로 해결.
- Mass conservation 체크(`sum(h) + totalCarriedSediment == initial sum(h)`)를 처음 float로 절대오차 비교했더니 `diff=0.015625`로 MISMATCH — 버그가 아니라 float32로 큰 합(~69210)을 반복해서 더할 때 생기는 정밀도 손실이었음(상대오차로는 `~2e-7`, float32 epsilon 수준). 누적 변수를 `double`로, 비교를 절대오차 대신 상대오차로 바꾸니 `~2e-10`으로 정상 통과. **큰 수를 반복해서 합산할 땐 절대오차보다 상대오차, float보다 double 누적이 안전하다**는 교훈.
