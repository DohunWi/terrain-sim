# 2026-07-17 — Droplet erosion 튜닝, TCP 소켓 골격 + RAII

### static 키워드 — 문맥마다 완전히 다른 의미

- 파일 스코프 함수/변수에 붙는 `static`은 **linkage**(다른 `.cpp`에서 이 이름이 안 보이게) 얘기지, 메모리 수명이랑 무관함. 반면 함수 **내부** 지역 변수의 `static int count = 0;`은 **수명**(호출마다 새로 안 만들고 프로그램 전체에서 한 번만 생성, 호출 사이에 값 유지) 얘기, 클래스 멤버의 `static`은 인스턴스 간 **공유** 얘기 — 같은 키워드가 위치에 따라 세 가지 별 관계 없는 걸 의미함.
- `droplet_erosion.cpp`의 `lerp`/`sampleHeightAndGradient`/`erode`/`deposit`/`dropletStep`을 처음 포팅할 때 `static`을 안 붙였었음 — 지금은 다른 파일에 같은 이름이 없어서 안 터졌지만, 나중에 다른 `.cpp`가 전역 `erode`나 `lerp`를 또 정의하면 링커가 "duplicate symbol" 에러를 냄. `perlin_noise.cpp`의 `fade`/`lerp`가 이미 `static`인 이유가 이거였음.
- 파이썬은 모듈마다 자기 네임스페이스가 있어서 이 문제 자체가 안 생김(`moduleA.lerp`/`moduleB.lerp`로 항상 구분됨) — C++은 `.cpp` 파일들을 따로 컴파일한 뒤 링커가 하나의 실행파일로 합칠 때 전역 심볼 테이블을 공유하기 때문에, 개발자가 직접 `static`으로 "이 이름은 파일 밖에 안 나간다"고 표시해야 함.

### C++ 연산자 오버로딩 — `operator=`

- `Socket& operator=(Socket&& other)`처럼 `=` 자체의 동작을 직접 정의할 수 있는 게 C++ 고유 기능. C는 struct 대입이 항상 고정된 memberwise 복사뿐이라 이 개념이 없고, C#은 `+`/`-`는 오버로딩 가능해도 `=`는 절대 불가능(항상 참조 재할당), 파이썬도 `__add__`/`__eq__`는 되지만 `=`는 항상 이름 재바인딩이라 커스터마이즈 불가능. `=`의 동작 자체를 프로그래머가 정의하는 건 이 두 언어엔 없는 개념.
- 리턴 타입이 `Socket&`(자기 자신의 참조)인 이유: `a = b = c;`처럼 대입을 연쇄로 쓸 수 있으려면 `b = c`라는 식 자체가 "대입 끝난 `b`"로 평가돼야 함 — 내장 타입 대입이 원래 그렇게 동작하는 관례를 따른 것.

### 멤버 초기화 리스트는 생성자 전용

- `Socket(int fd) : fd_(fd) {}`의 `: fd_(fd)` 부분(멤버 초기화 리스트)은 **생성자에만 있는 문법** — 소멸자나 일반 멤버 함수엔 이 자리가 아예 없음. 이유: 초기화는 "객체가 만들어지는 시점"에만 의미가 있고, 그 이후엔 이미 다 만들어진 객체라 몸체 안에서 그냥 대입(`fd_ = 값;`)하면 됨.
- `int fd_` 하나뿐인 지금은 몸체 안 대입이랑 차이가 거의 없지만, 멤버가 `const`거나 참조(`&`) 타입이면 생성 이후 재대입이 아예 불가능해서 반드시 이 리스트에서 값을 정해야 함 — 그래서 단순한 경우에도 관행적으로 항상 초기화 리스트를 씀.
- 생성자/소멸자는 리턴 타입 자리가 아예 없음(`void`도 아니고 진짜 아무것도 안 씀) — `Socket::Socket(int fd)`처럼 이름 앞에 아무것도 없는 게 정상.

### 헤더/cpp 분리 — 위치만 바뀌지 내용은 안 바뀜

- 클래스 전체를 헤더에서 cpp로 나눌 때 처음 시도가 틀렸던 지점: `socket.cpp`에 `#include "socket.h"` 없이 클래스 전체를 처음부터 다시 통째로 정의함 — 헤더의 선언들과 완전히 별개인, 아무도 안 쓰는 자기만의 클래스가 만들어진 셈. 실제로 링크해보면 `Undefined symbols: "Socket::Socket(int)"` 등으로 터짐(헤더는 "이런 함수가 있다"고 약속만 했는데, 어디에도 그 몸체가 안 붙어있어서).
- 올바른 규칙: 헤더엔 시그니처만(`Socket(int fd);` — 몸체도, `:`도 없음), cpp엔 `#include "socket.h"` 하고 각 메서드를 `Socket::메서드이름(...)` 형태로 클래스 밖에서 정의. 내용물은 원래 있던 거 그대로, 이름 앞에 `Socket::`만 붙이면 됨. `= delete`로 표시한 함수는 헤더 선언 자체가 끝(cpp에 따로 쓸 게 없음).
- 이 실수를 고치기 전/후를 실제로 컴파일+링크해서 에러 메시지로 직접 확인함 — "될 것 같은데 왜 안 되지"가 아니라 정확히 어떤 심볼이 안 잡히는지 링커 에러로 봄.

### 복사 금지가 진짜로 막아주는 문제 — double close를 직접 재현

- `Socket(const Socket&) = delete;`는 "새 규칙을 추가"하는 게 아니라, 컴파일러가 원래 자동 생성해줬을 그 함수 자리에 "삭제됨" 표시를 넣는 것. 시그니처가 똑같아서 오버로드 결정 과정에서 여전히 이 함수가 선택되는데, 몸체가 없다는 걸 확인하고 컴파일 에러를 냄.
- 왜 `int fd_` 하나 복사하는 게 위험한지: `fd_`는 C++ 타입으로는 그냥 정수지만 역할은 포인터랑 같음 — 커널이 관리하는 단 하나의 소켓을 가리키는 "열쇠 번호"일 뿐이라, 복사해도 그 번호가 가리키는 진짜 리소스가 하나 더 생기는 게 아님. `std::vector`가 복사돼도 안전한 이유는 그 내부 포인터를 얕은 복사하는 대신 새 힙 메모리를 할당해서 값을 통째로 복제하도록 **직접 구현**돼있기 때문 — "복사가 안전한가"는 포인터냐 값이냐가 아니라 "복사 생성자가 진짜 독립된 사본을 만들어낼 수 있느냐"에 달림.
- 이동 후 소멸자가 실제로 안전한지 직접 실험으로 검증: `socket()`으로 fd 3을 만들고 → `Socket`으로 감싸 이동시킨 뒤 스코프를 빠져나가게 해서 `close(3)`이 한 번 호출되게 하고 → 그 직후 새 소켓을 하나 더 만들어서 커널이 번호 3을 재사용하는지 확인(`stolen_fd=3`으로 실제 재사용됨) → 그 새 소켓을 포트 9123에 bind+listen 시켜두고 → 이동된(now `fd_=-1`) 원래 `Socket` 객체가 스코프를 빠져나가는 시점에 `lsof`로 포트 9123이 여전히 `LISTEN` 상태인지 확인. 만약 `fd_=-1` 체크가 없었다면 이 시점에 남의 소켓(fd 3, 방금 만든 새 소켓)이 실수로 닫혔을 것.

### 네트워크 기초 — IP/포트, TCP vs HTTP, OSI

- TCP는 전송 계층(L4)에서 "안정적인 바이트 스트림"만 보장하고 메시지 경계 개념이 없음 — 그래서 프로토콜을 직접 설계할 때 `[4바이트 길이][1바이트 타입][payload]` 같은 envelope를 우리가 직접 정해야 했음. HTTP는 그 위(L7)에서 이미 누가 정해놓은 특정 대화 규칙(요청줄+헤더+바디, GET/POST, 상태코드)일 뿐 — TCP=전화선, HTTP=그 위에서 쓰는 특정 화법.
- IP주소=어느 컴퓨터인지(L3), 포트=그 컴퓨터의 어느 프로그램인지 — 컴퓨터 하나가 여러 네트워크 프로그램을 동시에 돌리기 때문에 포트가 필요함. `127.0.0.1`(loopback)은 실제 네트워크 카드로 안 나가고 커널 안에서 바로 처리됨 — 로컬 개발 중인 core↔Unity 연결은 다 이 케이스.
- OSI 7-layer는 교과서 모델이고, 실제로 쓰이는 건 더 단순한 TCP/IP 4-layer(Link/Internet/Transport/Application) — OSI의 Session/Presentation/Application(L5~7)을 실무에선 그냥 하나로 뭉쳐서 다룸(Session을 독립적으로 구현하는 시스템이 거의 없어서). 우리 프로젝트 매핑: `socket()` 한 줄이 L3+L4(IP+TCP)를 OS가 대신 처리해주는 추상화, `docs/net-protocol.md`의 envelope+메시지 스키마가 L6/L7을 직접 설계한 부분.

### 드롭릿 침식 파라미터 튜닝 — "많이 깎인다"와 "패턴이 이상하다"는 다른 문제

- `numDroplets=3000`으로 64×64(4096칸) 지형에 돌렸더니 mass conservation은 정상(`relDiff~1.8e-8`)인데 시각적으로 지형 전체가 거의 균일한 회색으로 뭉개짐 — 이건 침식량이 아니라 **패턴**의 문제(전체 스무딩 vs 국소적 골짜기+퇴적)였음. `minSlope`를 낮춰봤지만 거의 변화 없었고, `numDroplets`를 700으로 낮추자 원래 노이즈 질감이 남으면서 국소적으로만 침식됨 — 4096칸 그리드에 3000개(각 최대 25스텝) 드롭릿이면 셀당 평균 여러 번씩 겹쳐 밟혀서 저역통과 필터처럼 작동했던 것.
- PGM은 이미지마다 자기 자신의 min/max로 독립적으로 정규화되기 때문에("몇 대 몇으로 대비가 세 보이나"가 실제 relief 변화를 반영 못함), before/after를 같은 min/max 기준으로 정규화하는 `writePGM` 오버로드를 추가하고서야 "진짜 relief가 줄었는지 vs 그냥 다시 스트레칭됐는지"를 믿을 수 있는 비교가 됨.
