# 2026-07-31 — 경사면 미끄러짐(법선/접선 분해), 에너지 보존 검증

### 곡면의 법선벡터 = 두 접선벡터의 외적
- 지형처럼 `y = h(x, z)` 형태로 표현되는 곡면은 `S(x, z) = (x, h(x,z), z)`로 매개변수화할 수 있고, 이 매개변수(`x`, `z`)에 대해 각각 편미분하면 그 지점에서 곡면에 접하는 두 벡터가 나온다: `∂S/∂x = (1, gradX, 0)`, `∂S/∂z = (0, gradZ, 1)`.
- 이 두 접선벡터를 외적하면 `(gradX, -1, gradZ)`가 나오는데, 이건 아래쪽을 향하니 외적 순서를 뒤집어 `(-gradX, 1, -gradZ)`로 — 이게 바로 "지형 그래디언트로 법선을 구하는 공식"의 정체다. 그냥 외운 공식이 아니라 실제로 손으로 외적을 풀어서 유도했다.
- 일반화하면: 임의의 곡면을 두 파라미터로 표현할 수 있을 때, 그 두 파라미터에 대한 편미분(=접선벡터 둘)을 외적하면 항상 그 곡면의 법선이 나온다. 증명은 간단하다 — 외적 결과 `n`은 정의상 두 입력 벡터 모두와 수직이고, 접평면 위의 모든 벡터는 이 둘의 선형결합으로 쓸 수 있으니 `n · (a·v1 + b·v2) = a(n·v1) + b(n·v2) = 0`, 즉 `n`은 접평면 전체와 수직이다. 높이필드는 이 일반 원리를 적용할 수 있는 특수 케이스일 뿐이었다.

### 벡터를 법선/접선 성분으로 분해하기 (내적 = 투영)
- 임의의 벡터 `v`를 단위벡터 `n̂` 방향 성분과 나머지로 쪼갤 수 있다: `v_normal = (v·n̂)·n̂`, `v_tangential = v - v_normal`. 내적 `v·n̂`이 "`v`가 `n̂` 방향으로 얼마나 있는지"를 나타내는 스칼라이고, 그걸 다시 `n̂`에 곱해서 벡터로 되돌리는 것.
- 물리적 의미: 공이 표면에 충돌할 때 `v_normal`(표면을 뚫고 들어가는 방향)만 지우고 `v_tangential`(표면을 따라가는 방향)은 남기면, 자연스럽게 "미끄러지는" 운동이 나온다. 평평한 바닥에서 이 분해는 그냥 "y만 0으로 만들기"와 같아지는데, 경사면에서는 그 "위/아래" 기준축이 지형에 맞춰 기울어질 뿐 원리는 동일하다.
- 부호는 저절로 맞춰진다: 공이 표면 쪽으로 움직이는 중이면 `v`와 `n̂`이 반대 방향이라 `v·n̂`이 음수가 되고, 그 음수를 `n̂`에 곱하면 방향이 자동으로 뒤집혀서 `v_normal`이 "파고드는 방향"을 가리키게 된다. 표면에서 튕겨 나가는 중이면 부호가 반대로 나온다 — 어느 쪽이든 코드에서 따로 방향을 분기 처리할 필요가 없었다.

### 링크 에러 (linker command failed) — 컴파일과 링크는 다른 단계
- 새로 만든 `vec3.cpp`를 `CMakeLists.txt`의 `add_executable(...)` 목록에 등록하는 걸 빼먹었더니 `linker command failed with exit code 1`이 났다. 컴파일 단계는 `vec3.h`의 함수 **선언**만 보고도 통과하지만(다른 어딘가에 진짜 구현이 있겠거니 하고), 링크 단계에서 그 실제 구현(정의)을 찾지 못하면 이런 에러가 난다.
- 지난 7월 11일 `perlin_noise.cpp`를 CMakeLists에 등록하는 걸 빼먹었던 것과 똑같은 종류의 실수 — 새 `.cpp` 파일을 만들 때마다 빌드 타겟에 등록했는지 확인하는 습관이 아직 완전히 자리잡지 않았다는 뜻. 반복되는 실수는 "체크리스트로 만들 가치가 있는 패턴"이라는 신호이기도 하다.

### 에너지 보존 검증으로 진짜 버그를 잡음
- 침식 시뮬레이션에서 mass conservation(질량 총합 불변)을 검증했던 것처럼, 물리 시뮬레이션에서는 에너지(`KE = ½mv²` + `PE = mgh`)가 대응되는 불변량이다. 공중에 떠 있을 땐 거의 보존돼야 하고, 충돌(비탄성 충돌 모델) 시엔 줄어들기만 해야지 늘어나면 안 된다.
- 이 하니스를 처음 돌렸을 때 실제 버그가 잡혔다: 지형에 오래 붙어서 미끄러지는 구간에서 `KE`가 완전히 고정된 채(소수점까지 똑같은 값) `PE`만 계속 올라가는 걸 발견 — 즉 오르막을 오르는데 속도가 전혀 안 줄어드는, 공짜로 에너지가 생기는 상황이었다. 원인은 충돌 처리 코드가 "접촉 중엔 중력을 아예 적용하지 않고, 이미 갖고 있던 속도를 법선/접선으로 나누기만" 하고 있었기 때문 — 한 번 접선 속도가 정해지면 오르막이든 내리막이든 그 속도 그대로 영원히 유지되는 구조였다.
- 고친 뒤 다시 돌려보니 `KE`와 `PE`가 정확히 반대로 움직이면서(오르막에서 `KE`가 `PE`로 정확히 전환) 총 에너지가 좁은 범위 안에서만 흔들렸다 — "돌아간다"만 보고 넘어갔으면 절대 못 잡았을, 눈으로 관찰하기 어려운 종류의 버그를 수치 검증이 잡아낸 사례.

### 공유 타입의 필드 이름은 소비자 기준으로 짓지 않는다
- `Heightmap::sample()`이 리턴하는 `HeightSample`의 `gradY`는 droplet erosion에선 heightmap 고유의 2D축 그대로지만, 물리 코드에선 실제로 world space의 `z`축 기울기다. "그럼 `gradZ`로 이름을 바꿔야 정확한 거 아닌가?"란 질문이 나왔는데 — 그러면 물리 쪽엔 맞아도 droplet erosion 입장에선(거긴 `z` 개념 자체가 없음) 틀린 이름이 된다.
- 결론: 여러 도메인이 공유하는 타입은 자기 고유의 중립적인 이름을 유지하고, 그 의미를 world-space 등 특정 도메인 언어로 "번역"하는 건 그 타입을 가져다 쓰는 **호출부**의 책임으로 남겨야 한다. 공유 컴포넌트를 한쪽 소비자 기준으로 이름 붙이면 반드시 다른 쪽이 틀려진다.
