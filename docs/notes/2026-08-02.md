# 2026-08-02 — Phase 2c 성능 엔지니어링: 측정 → 병렬화 → 알고리즘 병목 발견

### 할당(allocation)과 사용(reseed)을 분리하기

- `PerlinNoise(seed)`는 원래 생성자 안에서 "테이블 힙 할당"과 "RNG로 값 채우기"를 한 번에 했다. 문제는 매 episode reset마다 새 `PerlinNoise`를 만들면 이 두 가지가 항상 같이 일어난다는 것 — 값만 다시 채우고 싶어도 통째로 재할당해야 했다.
- `reseed(seed)`를 따로 만들어서 "채우기"만 분리했다. 생성자는 이제 `gx_`/`gy_` 메모리만 잡고, `reseed()`가 그 위에 값을 다시 씀. 이렇게 하면 인스턴스를 재사용하는 호출자는 할당 없이 매번 다른 시드로 재사용할 수 있다.
- 처음 구현할 때 `void reseed(unsigned seed){...}`를 클래스 스코프 없이 그냥 전역 함수로 써버려서, 함수 안에서 `gx_`/`gy_`(private 멤버)를 참조할 수 없는 컴파일 에러가 났다. `void PerlinNoise::reseed(unsigned seed){...}`처럼 `ClassName::`을 붙여야 "이 함수가 그 클래스 소속"이라는 게 성립하고, 그래야 암묵적 `this`를 통해 멤버에 접근할 수 있다는 걸 실제 에러로 확인했다. 헤더의 선언과 `.cpp`의 정의를 분리하는 C++의 관례상, 정의할 때마다 소속을 명시해야 한다는 걸 다시 체감함.

### 힙 할당이 멀티스레드 확장성을 갉아먹는 이유

- 처음엔 "이 512KB짜리 `PerlinNoise` 테이블 할당이 스레드 확장을 막는 병목 아닐까?"라는 가설(EXP-004)을 세웠는데, 실제로 테스트해보니 효과가 없었다(오히려 다른 이유로 악화됨).
- 나중에 진짜 병목을 찾았는데(`thermalErode`의 `findLowestNeighbor`), 이건 셀 하나·iteration 한 번마다 `std::vector`를 새로 만드는 코드였다. 64×64 grid, 10 iteration이면 reset 한 번에 **40,960번**의 힙 할당 — `PerlinNoise`의 "reset당 1번" 512KB 할당보다 빈도가 압도적으로 높다.
- 이걸 고치니(std::vector → std::array<4>, 이웃이 최대 4개로 고정돼 있으니 힙이 아예 필요 없음) 물리 코어 8개에서 처리량이 **거의 3배**(t=15.32, 통계적으로 압도적 유의)로 뛰었다. 배운 것: "할당 크기가 크다"보다 "할당 빈도가 높다"가 스레드 확장성에는 더 결정적인 변수였다. malloc은 여러 스레드가 공유하는 free-list/락을 두고 경합하기 때문에, 크기와 무관하게 자주 호출될수록 경합 기회가 늘어난다.

### 캐시 라인 정렬과 false sharing

- 여러 스레드가 각자 독립된 데이터만 만지는데도 처리량이 스레드 수만큼 안 느는 경우, 원인이 "공유 상태 경합"이 아니라 "캐시 라인 공유"일 수 있다는 걸 실제로 겪었다.
- `EnvSlot`(스레드마다 하나씩 배정되는 구조체)이 우연히 정확히 64바이트(캐시 라인 크기)였는데, `alignof`가 8이라 `std::vector<EnvSlot>`의 시작 주소가 64바이트 경계에 딱 맞는다는 보장이 없었다. 그러면 슬롯 크기가 캐시 라인과 같아도 모든 슬롯이 항상 같은 만큼 어긋나 있을 수 있고, 인접 슬롯끼리 캐시 라인을 공유하게 된다(false sharing) — 스레드 A가 자기 슬롯을 쓰는 순간 스레드 B의 캐시 라인도 무효화됨.
- `alignas(64)`를 구조체에 붙이면 "이 타입은 64바이트 배수 주소에만 놓여야 한다"는 걸 컴파일러가 강제하고, `std::vector`가 내부적으로 메모리를 요청할 때도 이 요구사항을 만족하는 주소를 받도록 보장된다. 실측으로 reset 처리량이 유의미하게(+21.7%) 개선됨을 확인.

### 성능 실험에서 통계적 유의성 검정하기

- 처음엔 "+30% 이상 개선하면 채택" 같은 라운드 넘버 기준을 썼는데, 반복 측정 7회로는 노이즈가 너무 커서 실제 신호(EXP-007의 `thermalErode` 대역폭 효과)를 완전히 놓친 적이 있다. 반복을 20회로 늘리고서야 신호가 드러났다.
- RL 평가에서 이미 쓰던 "100개 평가면 성공률 불확실성이 ±10%p 수준"이라는 이항분포 논리와 같은 종류의 문제라는 걸 깨닫고, perf 실험에도 같은 종류의 통계 검정을 도입했다: 반복 측정의 평균·표준편차로 표준오차(`SE = sd/sqrt(n)`)를 구하고, 두 그룹의 차이를 `t = Δ/sqrt(SE_a²+SE_b²)`로 판단(`|t|>=2.5`면 노이즈로 설명 안 되는 차이).
- 두 그룹이 이미 다른 두 평균의 "비율"(예: `speedup = mean_8thread/mean_1thread`)일 때는 이 공식을 그대로 못 쓴다는 것도 배웠다 — 비율의 표준오차는 delta method로 근사해야 한다(`SE_ratio ≈ ratio * sqrt((SE_a/mean_a)² + (SE_b/mean_b)²)`). "평균끼리 비교"와 "비율끼리 비교"가 통계적으로 다른 문제라는 걸 실제로 부딪혀서 알게 됨.

### 리팩토링이 "값을 안 바꿨다"를 증명하는 법

- `thermalErode`를 고칠 때 가장 중요했던 제약은 "빨라져야 한다"가 아니라 "결과가 리팩토링 전과 완전히(비트 단위로) 같아야 한다"였다 — 이 함수가 강화학습 환경의 `reset()`에 실제로 쓰이고, 그 환경이 "동결"된 상태라 결과가 조금이라도 달라지면 이미 기록된 평가 결과들과 안 섞이게 된다.
- 증명 방법: 리팩토링 전 코드를 그대로 복사해서 이름만 바꾼 사본(`thermalErodeRef`)을 테스트 전용으로 남겨두고, 20개의 서로 다른 seed에서 새 구현과 사본의 출력을 **셀 하나하나** `EXPECT_EQ`로 비교했다. 합계(체크섬)만 비교하면 서로 다른 셀의 오차가 상쇄돼서 숨을 수 있다는 걸 미리 짚고 셀 단위로 갔다.
- 이 검증이 있었기 때문에 "이 최적화는 공짜 성능 개선"이라고 자신 있게 결론지을 수 있었다 — 검증 없이 "로직 안 바꿨으니 당연히 같겠지"라고 넘어갔다면, FMA 명령어 축약이나 컴파일러 최적화로 인한 부동소수점 반올림 차이 같은 걸 놓칠 수 있었다(이번엔 실제로 안 났지만, 왜 안 났는지도 "컨테이너 타입을 바꾼 것 자체가 FMA를 유발하지 않는다"는 걸 근거를 들어 확인했음 — FMA 여부는 컴파일러 플래그/ISA가 결정하지 자료구조 선택이 결정하지 않는다).

### CI를 붙이고서야 드러난 표준 라이브러리 구현체 차이

- `.github/workflows/ci.yml`을 붙여서 `ubuntu-latest`(GCC/libstdc++)에서 처음으로 `core/`를 빌드해봤는데, 지금까지 macOS(AppleClang/libc++)에서는 한 번도 안 걸렸던 컴파일 에러가 바로 났다: `vec3.cpp`가 `sqrt()`를 쓰는데 `<cmath>`를 include하지 않은 상태였다.
- 원인은 "transitive include"였다 — `vec3.h`나 함께 include된 다른 헤더 중 하나가 내부적으로 `<cmath>`를 포함하고 있었고, 그게 libc++(macOS)에서는 우연히 `<iostream>` 같은 헤더의 구현 세부사항으로 딸려 들어왔던 것. libstdc++(Linux)는 같은 헤더를 다르게 구현해서 그 딸려오는 경로가 없었고, 그래서 "표준에 정의된 include"가 아니라 "이 컴파일러 이 버전에서 우연히 되는 include"에 의존하고 있었다는 게 실제 빌드 실패로 드러났다.
- 같은 클래스의 문제가 이 프로젝트에서 이미 여러 번 있었다는 걸 이번에 다시 확인함(`<cmath>`/`<cstddef>` 등, 2026-07-11/2026-07-18 로그) — "로컬에서 컴파일된다"는 "표준적으로 올바르다"의 증거가 아니고, 서로 다른 컴파일러/표준 라이브러리 조합에서 실제로 빌드해봐야 진짜로 검증된다는 걸 다시 체감. CI가 정확히 이 역할(다른 환경에서 자동으로 검증)을 한다는 걸 첫 실행에서 바로 보여준 셈.
