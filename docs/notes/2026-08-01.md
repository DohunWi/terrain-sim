# 2026-08-01 — Phase 2b RL 파이프라인 구축 + 평가 방법론 + 물리적 제약 조건 튜닝

### pyenv/conda가 같이 있을 때 PATH 우선순위와 CMake의 툴체인 탐색
- 이 프로젝트는 원래 pyenv(`python3` 3.9.1)를 써왔는데, RL 라이브러리(pybind11/gymnasium/stable-baselines3)는 conda `base`(3.13.5)에 새로 설치했다. 문제는 로그인 셸에서도 `pyenv shims`가 PATH에서 conda보다 먼저 온다는 것 — `CONDA_PREFIX` 환경변수는 정상인데도 CMake의 기본 `find_package(Python3)`는 PATH 순서를 따라가서 pybind11이 없는 pyenv 3.9.1을 집어버린다.
- 해결: `find_package(Python3)` 호출 전에 `CONDA_PREFIX`가 있으면 그 값을 `Python3_ROOT_DIR`로 미리 넣어준다. `Python3_ROOT_DIR`은 `FindPython3` 모듈이 다른 어떤 자동 탐색보다 우선하는 공식 힌트라, PATH 순서와 무관하게 원하는 인터프리터를 확실히 잡을 수 있다. `CONDA_PREFIX`가 없는 환경(CI 등)에서는 이 블록이 그냥 스킵돼서 기본 탐색으로 넘어가니 부작용이 없다.
- 새 `terrain_sim_py`(pybind11) CMake 타겟은 `find_package(pybind11 CONFIG QUIET)`가 실패하면 조용히 스킵되게 만들었다 — Python 환경이 없는 머신에서도 C++ 전용 타겟(`terrain_sim_core`, `tune_cli`, `physics_test`)은 그대로 빌드되게, 선택적 기능이 필수 빌드를 막지 않도록 하는 패턴.

### 평가용 seed 집합을 용도별로 분리하는 이유
- 정책을 튜닝할 때마다 매번 다른 무작위 seed로 평가하면, 여러 후보를 비교해서 "제일 나은 것"을 고르는 행위 자체가 암묵적으로 그 seed 집합에 과적합시키는 셈이 된다 — 사람이 수동으로 여러 결과를 보고 그 중 잘 나온 것을 채택하는 과정 자체가 일종의 (숨겨진) 모델 선택이기 때문.
- 그래서 용도별로 seed 범위를 미리 고정해서 분리했다: 개발 중 빠르게 나쁜 후보를 걸러내는 D20(20개, 반복 사용 가능), 채택 후보들을 정식으로 비교하는 V100(100개, 승산 있는 후보에만), 최종 설정을 다 정하고 나서 딱 한 번만 쓰는 T100. D20/V100은 반복 조회하면서 암묵적으로 "이 seed 집합에 맞춰 고르는" 효과가 생기지만, T100은 단 한 번만 쓰기 때문에 그런 편향에서 자유롭다 — 머신러닝의 train/validation/test 분리와 같은 발상.
- 학습된 정책 하나만 갖고는 "잘 학습됐다"를 주장하기 부족하다는 것도 이번에 체감했다. 목표로 직진만 하는 규칙 기반 컨트롤러, 완전 무작위 컨트롤러를 같은 조건에서 같이 돌려서 비교해야(`PPO 64% vs 직진 33% vs 무작위 0%`) "정책이 실제로 뭔가를 학습했다"는 근거가 된다 — 정책 하나의 성공률 숫자만으론 그게 높은 건지 낮은 건지 판단할 기준이 없다.

### 수평 힘만으로 오를 수 있는 최대 경사각은 asin이 아니라 atan
- 에이전트에 걸리는 액션은 수평 2D 힘(`Vec3(fx, 0, fz)`)뿐인데, 경사 `θ`인 표면의 접평면 방향으로 실제로 쓸 수 있는 힘은 그 수평 힘 전체가 아니라 `F·cosθ`만큼이다 — 표면에 접선 투영을 하면 수직 성분은 사라지고 수평 성분의 일부만 접평면에 남기 때문.
- 반대로 중력이 그 접평면을 따라 끌어내리는 힘은 `m·g·sinθ`. 등반 가능 조건은 `F·cosθ ≥ m·g·sinθ`, 양변을 `cosθ`로 나누면 `F ≥ m·g·tanθ` — 그러니까 한계각은 `θmax = atan(F_MAX / (m·g))`다.
- 처음엔 `asin(F_MAX/(m·g))`로 잘못 썼는데(`F_MAX=5`, `m·g=9.8` 기준 `asin`은 30.7°, `atan`은 27.0°), "F가 힘 그 자체가 아니라 접평면에 투영된 성분이어야 하는데 그럼 코사인이 곱해져야 하는 거 아닌가"를 되짚으면서 잡아냈다. 힘의 방향(수평 고정)과 그 힘이 실제로 작용하는 면(경사면)이 다를 때, "이 값이 그 면 위에서 몇 %만큼 유효한가"를 놓치면 이런 식으로 삼각함수가 바뀐다.

### 축별 clip과 L2 norm clip은 다른 제약이다
- 2D 연속 액션(`fx`, `fz`)을 `F_MAX`로 제한할 때, `clip(fx, -1, 1) * F_MAX`처럼 축마다 따로 자르면 대각선 방향(`fx=1, fz=1`)에서 최종 힘의 크기가 `F_MAX·√2`까지 나온다 — 정사각형 제약 영역의 대각선이 변보다 `√2`배 길기 때문.
- "F_MAX는 방향과 무관한 최대 힘"이라는 전제(등반 가능 여부를 좌우하는 물리량)를 지키려면, 먼저 액션 벡터의 L2 norm이 1을 넘지 않게 정규화한 뒤 `F_MAX`를 곱해야 한다(`norm > 1이면 action /= norm`) — 그래야 어느 방향으로 밀든 힘의 크기가 정확히 `F_MAX` 이하로 유지되는 원(circle) 제약이 된다.
- 이 버그는 눈으로 코드만 봐서는 "그럴듯해 보이는" 코드였다 — 강화학습 정책이 실제로 이 여유분(방향에 따라 최대 40% 더 센 힘)을 학습에 이용했을 수도 있어서, 버그를 고친 뒤엔 그 이전 학습 결과를 폐기하고 다시 학습했다.

### 시스템의 실제 상한을 먼저 재고 나서 파라미터를 조정한다
- 지형이 에이전트를 실제로 막고 있는지 확인하려고, 100개 지형 시드에서 셀별 경사각 분포를 직접 측정하는 스크립트를 만들었다. 결과: 침식 파라미터(`TALUS_ANGLE`)를 아무리 세게 조정해도 `theta_max`(27.0°)를 넘는 셀이 하나도 없었다.
- 원인을 더 파보니, 침식 전 원본 fbm 노이즈 자체의 최대 경사가 이미 24.8°로 `theta_max`보다 낮았다 — 즉 침식은 "있는 경사를 깎아내는" 역할만 하지 "없던 경사를 만들어내는" 역할은 못 하는데, 애초에 원본 노이즈의 천장 자체가 목표 임계값보다 낮았던 것. 침식 강도를 조정하는 건 애초에 이 문제를 풀 수 있는 레버가 아니었다.
- 교훈: 파라미터를 조정해서 원하는 결과가 안 나올 때, "이 파라미터가 영향을 주는 값의 이론적 상한이 애초에 목표보다 낮은가"부터 확인하는 게 무작정 스윕하는 것보다 빠르다. 이번엔 물리 없이 지형 생성만 재현하는 가벼운 분석 스크립트(100개 지형에 1.4초)를 만들어서 실제로 몇 초 만에 이 상한을 찾을 수 있었다 — 학습(각 4~5분)을 여러 번 돌려보며 감으로 찾는 것보다 훨씬 저렴했다.

### 한 파라미터를 바꾸면 다른 파라미터의 전제도 같이 깨질 수 있다
- 지형을 실제로 막히게 만들려고 `F_MAX`를 5.0→2.0으로 낮췄더니(가속도 `a=F/m`도 같이 줄어듦), 시간초과 비율이 5%→55%로 폭증했다. `MAX_STEPS=500`이라는 값은 원래 `F_MAX=5.0` 기준으로 "적당하다"고 암묵적으로 가정된 값이었는데, `F_MAX`만 따로 바꾸면서 그 가정이 깨진 것.
- 원인을 확인하려고 "목표로 직진만 하는(우회 없는)" 단순 컨트롤러를 같은 물리 조건에서 돌려봤다 — 지형이 전혀 안 막는 상황에서도 성공한 에피소드의 중앙값이 500스텝 중 376스텝이었다. 이건 "우회하느라 오래 걸린다"가 아니라 "그냥 이동 자체가 느려서 시간이 부족하다"는 신호였다.
- `MAX_STEPS`를 1000으로 올려서 시간초과는 해결됐지만, 이번엔 맵 이탈이 20%→75%로 폭증했다 — 시간에 쫓겨 일찍 멈추던 실패가, 시간이 넉넉해지자 방황하다 지도 밖으로 나가는 실패로 형태만 바뀐 것. 하나의 실패 지표(시간초과)를 없앴다고 문제가 해결된 게 아니라, 그 밑에 가려져 있던 다른 실패 원인(관측값에 경계 정보가 없음)이 그제서야 드러난 셈이다.
