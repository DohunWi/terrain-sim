# 2026-07-11 — Phase 1: Perlin/fBm 노이즈 지형 생성

### Gradient noise (Perlin) 개념

- Value noise(격자점에 랜덤 스칼라 + 보간)와 Gradient noise(격자점에 랜덤 방향벡터 + 내적)의 차이: value noise는 격자점 근처에서 뭉친 느낌(블롭 아티팩트)이 남는데, gradient noise는 "거리벡터·gradient의 내적"을 쓰기 때문에 격자점 자체에서 항상 0이 나오면서 훨씬 유기적인 패턴이 나옴.
- 정수 격자점에서 노이즈 값이 항상 0인 이유: 그 지점에서의 변위벡터가 `(0,0)`이라 어떤 gradient와 내적해도 0.
- 변위벡터(displacement vector)와 "거리"는 다른 개념 — 거리는 항상 0 이상(방향 없음)인데, 여기서 쓰는 건 부호 있는 벡터(`x - x0`). 부호가 있어야 gradient 방향과 "같은 방향인지 반대 방향인지"가 내적에 반영됨. 1D에서는 벡터가 성분 1개짜리라 그냥 부호 있는 스칼라로 보이는 것뿐.
- Fade 함수(`6t^5 - 15t^4 + 10t^3`)를 쓰는 이유: 순수 linear interpolation은 셀 경계에서 2차 미분이 불연속이라 격자 무늬가 살짝 비쳐 보임. fade는 `t=0,1`에서 값·1차미분·2차미분이 모두 0이 되도록 설계된 다항식이라 경계가 완전히 매끄럽게 이어짐.
- Bilinear interpolation은 "축마다 한 번씩, 총 2번"이 아니라 **lerp 3번**(x축으로 두 변 각각 한 번씩 + 그 결과를 y축으로 한 번 더)이라는 걸 손으로 따져보고서야 이해됨 — "4점을 1점으로 줄이려면 이항 연산(lerp)을 3번 트리처럼 묶어야 한다"는 감으로 일반화 가능.
- fBm(fractal Brownian motion)은 별개 알고리즘이 아니라 "이미 만든 노이즈 함수를 옥타브마다 주파수 ↑ / 진폭 ↓ 로 여러 번 더하는 것" — 저주파·큰 진폭 옥타브가 지형의 큰 형태를, 고주파·작은 진폭 옥타브가 표면 디테일을 담당. 이 순서를 거꾸로 하면(진폭도 커지고 주파수도 커지면) 미세하고 격렬한 옥타브가 전체를 지배해서 지형이 아니라 가시밭처럼 뾰족뾰족해짐 — 실제로 버그로 이 상황을 겪어봄(아래 참고).

### 디버깅 사례 (practice/에서 1D → 2D → fBm 순으로 직접 구현하며 마주친 것들)

- **변위벡터에 `t`를 잘못 씀**: `dx0 = t - x0` (원래는 `x - x0`). `t`는 이미 `x - x0`로 한 번 계산된 값이라 여기서 또 `x0`/`x1`을 빼면 다른 식이 됨. 근데 `x0 = 0`인 첫 번째 셀에서는 `t - x0`와 `x - x0`가 우연히 같아져서 버그가 안 드러나고, `x0`가 0이 아닌 두 번째 셀부터 값이 어긋남 — "특정 조건에서만 우연히 맞는 코드"가 제일 잡기 어려운 버그 유형이라는 걸 체감.
- **gradient 테이블을 항상 `g[0]`/`g[1]`로만 인덱싱**: 어느 셀이든 상관없이 같은 두 gradient를 재사용해서, 셀마다 달라야 할 패턴이 전부 똑같이 반복되는 문제. 고정 크기(256) 테이블 + `인덱스 % 256`(나머지 연산으로 순환)으로 해결 — 실제 Ken Perlin 원본 구현도 이 방식(permutation table + wraparound)을 씀. 좌표가 아무리 커도 배열 범위를 미리 예측할 필요가 없어짐.
- **`float y0 = float(y)` 오타** (`floor(y)`를 쓰려다 `float(y)`로 씀 — 형변환과 내림 함수를 착각): `y0`가 사실상 `y`와 같아져서 `ty`, `dy0`가 항상 0이 됨 → y좌표가 결과에 전혀 반영 안 되는 버그. 증상은 "모든 행(row)이 동일한 값"으로 나타났는데, `y`가 정수 경계를 넘는 순간(배열 인덱스로 쓰이는 `(int)y0`가 바뀌는 지점)에만 다른 값이 나와서 원인 추적에 단서가 됨.
- **fBm 진폭/주파수 계산 실수**: `(i+1)*persistence`, `(i+1)*lacunarity`처럼 옥타브 번호에 비례해서 계산 — persistence가 1보다 작은데도 `(i+1)`을 곱하니 진폭이 오히려 커지는 반대 방향 버그. 결과가 실제로 "뾰족뾰족"하게 나와서 사전에 예측했던 실패 시나리오와 정확히 일치하는 걸 확인. 고친 뒤에도 `frequency`/`amplitude` 초기값을 `lacunarity`/`persistence`로 잘못 잡아서, 가장 중요한 "옥타브 0(주파수 1, 진폭 1 그대로)"이 통째로 빠지는 off-by-one이 한 번 더 있었음.
- **`core/src/noise/perlin_noise.cpp`로 포팅 중 회귀**: `noise2D`의 4개 코너 영향값 계산에서 `x1`/`y1` 쪽 코너인데도 전부 `dx0`/`dy0`를 재사용 — 컴파일러의 `-Wunused-variable` 경고(`dx1`, `dy1`을 선언만 하고 안 씀)가 결정적 단서였음. 셀 경계에서 값이 매끄럽게 0으로 수렴해야 하는데 튀어 올랐다가 뚝 끊기는 현상으로 실제로도 확인됨 — **컴파일러 경고를 진짜 버그 탐지 도구로 쓴 사례**.

### C++ 문법/설계

- `std::unique_ptr<T[]>`(배열 전용 특수화): `new[]`로 할당한 메모리를 소멸시킬 때 `delete`가 아니라 `delete[]`를 써야 하는데, 배열 버전 `unique_ptr`가 이 차이를 자동으로 처리해줌.
- `unique_ptr` 멤버가 있는 클래스는 복사 생성자가 자동으로 `delete` 처리됨(컴파일 에러) — Phase 0에서 "unique_ptr이 왜 복사가 안 되는지" 개념으로만 알던 걸, 512KB짜리 gradient 테이블을 담은 실제 클래스 설계에서 마주침. 이동(`std::move`)은 정상 동작 — 포인터만 옮겨가고 재할당/복사가 없음.
- 멤버 초기화 목록(`: gx_(...), gy_(...)`)은 C#/Python엔 없는 문법 — 생성자 본문이 실행되기 *전에* 멤버를 바로 그 값으로 만드는 구간. `unique_ptr<float[]>`를 여기서 `make_unique`로 할당해두면, 본문에서는 이미 유효한 메모리에 안전하게 값을 채우기만 하면 됨.
- `static constexpr int TABLE_SIZE = 256;`: 인스턴스마다 따로 저장할 필요 없는 클래스 차원 상수. 처음엔 그냥 `int` 멤버로 선언해서 초기화가 안 된 채로 생성자에서 쓰일 뻔한 위험한 상태였음.
- 파일-로컬 함수에 C에서 쓰던 `static`을 그대로 재사용 가능 — `.cpp`에 아무 표시 없이 정의한 함수는 외부 링키지를 가져서, 다른 `.cpp`가 같은 이름의 함수를 정의하면 링크 에러가 남. `fade`/`lerp`처럼 이 파일 안에서만 쓰는 헬퍼 함수는 `static`을 붙여 내부 링키지로 제한.
- VSCode IntelliSense가 `std::numbers`(C++20)를 모른다고 오류 표시했는데, 실제 빌드(`-std=c++20`)는 전혀 문제없었음 — IntelliSense의 파싱 기준(C++ 표준 버전)이 실제 빌드 설정과 별개로 관리된다는 걸 확인, `.vscode/c_cpp_properties.json`에 `cppStandard: c++20` 추가해서 해결.

### 침식 파라미터 실험 (탐색적, 미해결)

- Phase 0 열침식의 talus angle(1.0)은 스파이크 데모(이웃 높이차 ~12) 기준으로 맞춰진 값이라, 이번에 생성한 fBm 지형(이웃 높이차 ~0.05~0.2)에는 완전히 무의미한 값이었음 — 침식 전/후 결과가 픽셀 단위로 완전히 동일하게 나옴. **파라미터는 지형의 스케일에 상대적**이라는 걸 실감.
- talus angle을 낮춰서(0.02, 0.1) 실제로 침식이 발동하게 만들었더니, 부드럽게 깎이는 대신 격자무늬 같은 speckle 패턴이 나옴. Phase 0에서 "질량 보존은 되지만 등방성이 아니다"로 남겨뒀던 known limitation(단일 최저 이웃 재분배의 방향 편향)이, 경사가 뚜렷한 지형에서는 안 보이다가 이웃끼리 높이가 비슷비슷한 완만한 지형에서는 반복마다 재분배 방향이 뒤집히는 형태로 표면화된 것으로 추정 — 다음 세션에서 비례 다중 이웃 재분배로 고쳐볼 대상.
