# 2026-07-18 — TCP 프로토콜 완성 (envelope/params/heightmap 직렬화), 정수 오버플로우 버그 사냥

### 파일 디스크립터 / socket-bind-listen-accept 4단계 — 왜 이렇게 쪼개져 있나

- fd는 리소스 자체가 아니라 커널의 "열린 리소스 테이블" 한 칸을 가리키는 정수 색인일 뿐. 유닉스가 파일/파이프/소켓/디바이스를 전부 같은 `read()`/`write()`/`close()`로 다룰 수 있는 이유가 이거고, `send()`/`recv()`가 `read()`/`write()`랑 닮은 것도 우연이 아님 — 소켓도 결국 "또 다른 종류의 fd". 다만 "모든 리소스가 파일"은 과장이고, 정확히는 "I/O 스트림처럼 다룰 수 있는 것들"만 이 인터페이스로 통일돼 있음(메모리, CPU 스케줄링은 fd로 안 다룸).
- `socket()`/`bind()`/`listen()`/`accept()`가 4단계로 나뉜 이유는 각 단계가 서로 다른 용도로 독립적으로 필요하기 때문 — `bind()`는 서버만 필요(클라이언트는 OS가 알아서 임시 포트 배정), `listen()`은 능동↔수동 모드 전환, `accept()`는 listen 소켓과는 별개의 새 fd(연결 전용)를 만들어냄. listen 소켓은 계속 새 연결을 받고, accept로 나온 fd는 그 연결 전용 — 이 두 fd의 분리가 핵심.

### TCP는 왜 "메시지"를 모르는가, 그래서 왜 TCP를 골랐나

- TCP는 메시지가 아니라 바이트 하나하나에 순서번호를 매겨서 "신뢰할 수 있는 연속된 스트림"이라는 착각을 만들어주는 게 목적 — `send()`를 몇 번 나눠 불렀는지 자체가 받는 쪽에 전달될 방법이 없음(Nagle 알고리즘이 작은 전송을 합쳐 보내기도 함). 그래서 `docs/net-protocol.md`의 envelope(`[4바이트 길이][1바이트 타입][payload]`)가 필요했던 것 — TCP가 안 주는 "메시지 경계"를 애플리케이션 계층에서 직접 만든 것.
- UDP 대신 TCP를 고른 이유를 문서화(`net-protocol.md` "왜 TCP인가" 섹션): heightmap 데이터는 일부 유실되면 안 되는데(UDP는 신뢰성 없음) + UDP 데이터그램 한 개로 heightmap이 안 들어갈 만큼 큼(직접 쪼개고 재조립해야 함, TCP가 이미 해주는 일) + 이 프로토콜은 실시간 스트리밍이 아니라 request-response라 UDP의 저지연 장점이 애초에 필요 없음. "UDP 장점은 우리가 안 쓰고, UDP 단점은 우리가 못 견딘다"로 요약됨.

### 부호 있는 정수 오버플로우는 컴파일러가 안 잡아주는 UB

- `readEnvelope`에서 `header[3]*256*256*256` — `header[3]`은 `uint8_t`지만 산술 연산에 쓰이면 `int`(32비트, 부호 있음)로 자동 승격됨. `header[3]>=128`이면 이 곱셈이 `int`의 최댓값(약 21억)을 넘어서 signed overflow — undefined behavior.
- 근데 실행 결과는 우연히 정확했음: GCC가 오버플로우를 그냥 2의 보수로 wraparound시켜서, `uint32_t`로 처음부터 계산한 것과 같은 비트 패턴이 나온 것. `-fsanitize=undefined`로 다시 돌려보니 `runtime error: signed integer overflow: 13107200 * 256 cannot be represented in type 'int'`가 정확히 잡힘 — "결과가 맞다"와 "정의된 동작이다"는 다른 문제라는 걸 직접 확인. 고치는 법: 곱하기 전에 각 바이트를 `(uint32_t)`로 캐스팅해서 애초에 부호 없는 타입으로 연산되게 함(부호 없는 정수는 오버플로우해도 wraparound가 표준에 정의돼 있어서 UB가 아님).

### 배열은 포인터로 decay된다 — `*array`는 배열 전체가 아니라 첫 원소

- `serializeHeightmap`에서 `uint8_t width[4]`를 채운 뒤 `bytes.push_back(*width)`로 통째로 넣으려 했던 실수. `width`(배열 이름)는 포인터로 자동 변환(decay)되고, `*width`는 그 포인터를 역참조한 것 — 즉 `width[0]`과 완전히 같음. `push_back`은 한 번에 원소 하나만 받으니, 4바이트 중 1바이트만 들어가고 나머지 3바이트는 조용히 버려짐.
- 직접 실험으로 확인: `push_back(*width)` 한 번 호출 후 `bytes.size()`가 4가 아니라 1. 고치는 법은 `width[0]`~`width[3]`을 각각 따로 `push_back` — 배열을 통째로 벡터에 붙이는 지름길은 없고, 명시적으로 원소별로 넣어야 함.

### `std::optional`, `std::bit_cast` — C++17/20이 준 새 도구

- `std::optional<Envelope>`는 "값이 있을 수도 없을 수도 있다"를 타입으로 표현 — C#의 `Nullable<T>`(`T?`)와 감각이 같음. 실패는 `bool` + out-파라미터 대신 그냥 `return std::nullopt;`, 성공은 `return Envelope{...};`로 표현.
- `float`는 비트 연산(`&`, `<<`)을 아예 못 씀 — IEEE-754로 저장된 값이라 "산술적 값"이 아니라 "저장된 비트 패턴"을 꺼내야 정수처럼 바이트 단위로 쪼갤 수 있음. `std::bit_cast<uint32_t>(floatValue)`(C++20)가 이걸 안전하게 해줌 — 이후엔 정수 필드(`length` 등) 인코딩할 때 쓴 시프트/마스킹 코드를 그대로 재사용 가능. 왕복 검증(직렬화 → 역직렬화)으로 음수/소수 float도 정확히 복원되는 것 확인함.

### 부호 있음/없음 비교 경고 — 오늘 세 번 반복된 같은 실수

- `io.cpp`(`recv`/`send` 리턴값을 `size_t`로 받아서 `-1`이 거대한 양수로 wraparound), `protocol.cpp`(`int i/j` vs `uint32_t w/h` 루프 비교), `params.cpp`(`.find()`가 리턴하는 `size_t`를 `int idx`로 받음) — 세 번 다 "값은 우연히 맞는데 타입이 틀림" 패턴. `-Wsign-compare`(`-Wall`/`-Wextra`에 포함)가 매번 잡아줬음 — 표준 라이브러리 함수(`.find()`, `send()`/`recv()`)가 실제로 뭘 리턴하는지 확인하고 그 타입 그대로 받는 습관이 필요하다는 걸 세 번 반복해서 체감함.
